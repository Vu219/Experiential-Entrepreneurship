## 2. Logic Chain

1. **Schema Check (Observation 1.1 & 1.2)**:
   The database table `content_versions` has columns `voice_aligned`, `voice_score`, and `voice_notes` from baseline V1 migration. The JPA entity `ContentVersion` maps these columns. Therefore, the defect is not a lack of database support or entity mapping.

2. **Source Population (Observation 1.4)**:
   When content is first generated (`ContentGenerationWorkerServiceImpl` + `ContentItemMapper.toGeneratedVersion`), `voiceAligned`, `voiceScore`, and `voiceNotes` are properly populated from `GeneratedContentResult.brandVoiceCheck`.

3. **Loss Mechanism during Formatting (Observation 1.5)**:
   When the user runs platform formatting, `ContentFormattingWorkerServiceImpl.savePlatformResult` creates new `ContentVersion` entities via `contentFormattingMapper.toContentVersion(payload)`. `ContentVersionPayload` does not have brand voice fields. The worker specifically copies `script` and `mediaPrompt` from `source` (`source.getScript()`, `source.getMediaPrompt()`), but does NOT copy `source.getVoiceAligned()`, `source.getVoiceScore()`, or `source.getVoiceNotes()`. Consequently, newly created platform versions have `null` for all three fields.

4. **UI Failure Propagation (Observation 1.3 & 1.5)**:
   When frontend calls `GET /content-items/{itemId}`, the backend serializes the formatted version using `ContentVersionResponse` where `voiceScore` is `null`. Frontend converts `null` to `0`, resulting in the "Chưa kiểm tra" badge on `ContentViewPanel` (Acceptance Criterion R1 & R3 violated).

5. **API Update Limitation (Observation 1.6)**:
   When user edits content or triggers a brand voice recheck, `PUT /content-items/{itemId}/versions/{versionId}` is called. Because `ContentVersionUpdateRequest` lacks `voiceAligned`, `voiceScore`, and `voiceNotes`, and because `versionContent()` omits them from dirty checking, Brand Voice updates cannot be sent, accepted, or saved.

6. **Scheduling Policy Roadblock (Observation 1.7)**:
   In `PostScheduleServiceImpl`, `score == null` is treated as failing the threshold (`score == null || score < threshold`). Therefore, users who enabled brand voice blocking cannot schedule formatted posts due to the lost score.

## 3. Caveats

1. **AI Service Standalone Recheck Route**:
   The Python AI service does not currently have a dedicated `POST /check-brand-voice` endpoint (it only checks brand voice during `POST /generate`). Therefore, rechecks in the UI can either use the existing heuristic/client check (or mock service) and persist via `PUT /content-items/{itemId}/versions/{versionId}`, or the AI service can add a standalone recheck route if requested by Survey 1. The backend update API changes proposed here support both models transparently.
2. **Soft Delete and Re-formatting**:
   When re-formatting an already formatted version, `savePlatformResult` resolves `source` using `active.getSourceVersionId() != null ? active.getSourceVersionId() : active.getId()`. Hence, inheriting from `source` correctly traces back to the original generated version even during repeated re-formatting.
